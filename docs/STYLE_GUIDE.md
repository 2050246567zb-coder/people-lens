# 文风与提示词

没有本地训练模型。取数和抽样是确定规则，写作由提示词约束；不同模型的措辞仍可能不同。

## 人物介绍

像向朋友介绍刚认识的人。默认约 180 字、3–5 句连贯中文，开头直接说有证据的整体印象，再自然带出公开背景、反复出现的兴趣、做过的项目、生活方式、审美或表达习惯。没有资料的方面跳过，不强行凑全。

概括要有具体行为或内容例子支撑。工作、学校、经历须是本人自述，写“主页提到”“分享过”。不能从编程猜职业、从追星猜性别、从地点猜住址。“看起来”不能替无依据的猜测开脱。少量帖子不用于固定人格或心理诊断。

不写标题、列表、标签堆叠、账号运营报告、逐篇报菜名、寒暄、分析过程、来源编号或回复建议。只有标题时明确“仅从标题看”。自定义提示词改变关注点，不能降低证据要求。

以下是虚构写法示例，不是用户资料或实测模型结果：

> 这位看起来喜欢自己动手折腾东西，主页提到做产品设计，分享过给小装置接 API、调整外壳的过程。平时也会聊机械键盘和桌面布置，比起只晒成品，更愿意把踩过的坑和具体做法讲出来。

避免改写成“该用户是兼具创新意识与生活美学的复合型创作者，拥有强大的技术实力”。形容词没有增加事实，也容易夸大。

## 小众词解释

同一次请求先输出介绍，再输出分隔符和词义：

```text
人物介绍正文
<<<GLOSSARY>>>
[{"term":"API","meaning":"软件之间约定好的调用方式，用来获取数据或使用功能。"}]
```

最多 6 个，必须是正文出现的原词，优先圈内术语、缩写、梗、小众专名。释义约 20–60 字，结合语境，圈外人能懂。不解释常用词、不猜词源、不补充对人的新判断；歧义过大或不确定就省略，没有词输出 `[]`。

`analysis.js` 隐藏完整及拆包中的分隔符，词义 JSON 失败也保留正文。前端只高亮首次出现的原词，长词优先，英文边界避免把 CP 标进 CPU。纯文本渲染；悬停、聚焦或点击查看释义，不增加请求。

## 回复建议

先回应对方当前这句话，再参考人物介绍调整表达。结合当前笔记、目标评论、必要上文、人物介绍生成 3 条不同角度的自然候选，通常每条 20–80 字：自然接话、追问细节、轻松表达。不要为凑风格强行玩梗。

不能误回 parent；`mode=post` 时回复笔记本身。没有图片或视频输入，不假装看过。不写“我分析了你的主页”，不编造用户经历、身份、关系或承诺；不要随便写“我也是”“我已经关注了”。不用人物画像写操纵或政治劝服话术。

协议为 JSON 数组 `[{"label":"自然接话","text":"…"},…]`，最多 3 条，label 最多 12 字、text 最多 280 字。只显示解析后的候选。换一组附带上一组以避免重复。

## 权威入口

- 人物 system、词义和 user 模板：`extension/lib/api.js:modelMessages`。
- 建议 system 和上下文：`extension/lib/replies.js:replyMessages`。
- [prompts/](prompts/) 是原文快照，保留 `${settings.summaryLength}`、`${GLOSSARY_MARKER}` 等占位符；实际调用以源码为准。

改文风优先修改提示词，不通过后处理硬塞评价词。改输出协议同步流式解析和缓存兼容。当前未授权测试，不通过真实 API 试写。
